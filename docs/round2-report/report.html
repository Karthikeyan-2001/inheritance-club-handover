Inheritance

They left. Their promises didn’t.

Inheritance is a working handover system for university student clubs. It reads a club’s WhatsApp exports, meeting minutes and Trello board, and builds a ledger of what the outgoing committee still owes: promises made to people, and duties that recur every semester with the approvals they need. Every entry links to a verified quote from its source, anything the records cannot support is shown as a gap, and nothing reaches the incoming lead until the outgoing lead and the faculty advisor have reviewed and approved it. Each role sees only what its permissions allow, enforced by the database.

How a judge can try it without help

On Sign in, Explore a built handover gives you a private copy of a year of a synthetic IoT club (1,961 messages in five files at four access levels) with its ledger already built by Claude, version 1 approved and six items left for you to review. Start from your own files gives you an empty club: download the four sample files from Connect, import them, press Build the ledger, then review, approve and hand over. Both run as four accounts of your own (outgoing lead, faculty advisor, incoming lead, treasurer) that you switch between from the menu.

The workflow, as built

The five steps of the brief are five pages of the product. Each step below is working on the live link.

StepWhoWhat happens
ConnectOutgoing lead, advisorUpload WhatsApp .txt (Android, iPhone), Trello JSON and minutes (.md, .docx), several at once. Set an access level per file (everyone, committee, finance, private); one-to-one chats default to private. Confirm authorisation; the AI provider is named. A “what was read” report counts every dropped line by reason. Files are parsed, not stored.
ReconstructSystemOne button runs small background steps: commitments (who owes whom, what, by when), recurring duties (cadence, approval, approver, lead time, next due, start-by), follow-up checks, context notes (decisions, contacts, risks, dependencies) and matching of the same obligation across sources. A timeline shows every message the role may read.
VerifySystemEvery quote is checked by code against its message, then again by the database. A fixed rule sets trust and status. The Docket lists records that disagree; the Gaps tab lists what is missing. Every quote opens its source message, highlighted.
ReviewOutgoing lead, advisorAccept, edit, reject or reopen each item with a reason; mark linked records “same” or “not the same”. The lead marks the draft ready; the advisor rules on conflicts and approves an immutable version. History shows every action.
HandoverIncoming leadThe approved version as her role reads it: people waiting on her, a calendar of duties with “Start now” and “Overdue”, sealed placeholders for what she may not read. She accepts, questions or declines each item; the outgoing lead and advisor reply to questions.

Trust states, on every item, set by a rule, never by the model: CORROBORATED two independent records agree · SOURCED one verified quote · INFERRED only implied, never shown as fact · CONTRADICTED records disagree · GAP no evidence kept.

03Architecture

Architecture and data flow

UploadsWhatsApp, Trello JSON, minutes; level per file
Parsersone event shape, IST times, dropped lines counted
Jobssmall steps in a jobs table, driven by the browser
Modelone adapter, Zod-validated output, cached by prompt hash
Validatorquote check, grounding, status and trust rules, provenance
Review and viewssign-off, immutable versions, RLS-filtered pages

Everything lives in one Postgres database (Supabase). Shaded boxes carry the trust and permission logic; both run inside the database as well as in code.

  • One codebase. Next.js 16 App Router in TypeScript (strict): pages, server actions and API routes. Hosted on Vercel Hobby; database, auth and RLS on Supabase Free.
  • Import. A server action parses the upload and calls import_source(), which runs as the signed-in user, so row-level security checks every row written. Only the events, a counts-only summary and the file’s SHA-256 are kept.
  • Build. planRun writes one job per chunk of messages, duty batch, follow-up check and match batch. The browser calls POST /api/jobs/run-next until all are done, so no serverless call runs long. Each job reads only what its user may read, through RLS; job rows hold ids and counts, never text.
  • Model calls go through generateStructured(): a Zod schema turned into structured output, validated again, one retry, a cache keyed by the prompt’s hash, a daily call budget, and typed errors. Prompts never mix access levels.
  • Storage functions (add_extracted_commitment, add_recurring_duty, record_followup, link_obligations) repeat every check in SQL. Triggers set each item’s access level from its cited messages, compute trust and status, open docket entries and write the audit log.
  • Review goes through review_obligation(), mark_ready(), approve_version() and rule_conflict(); a direct update by a user is refused without a reason. Versions, acknowledgements, replies and audit rows are immutable for every role.
  • Pages filter first, then render: every query runs as the viewer, so a page can only show rows the database returned to that role. The incoming lead reads approved version rows only, never the working ledger.
04Trust

Trust, permissions and privacy

  • The model proposes; code decides. A claim is stored only if its quote is a normalised substring of the cited message. Hedged promises (“maybe”, “will see”, Tamil-English “paakalam”) are dropped. A description or note may not name a person or number missing from its own message. Dates come from code. Every rejection is counted.
  • Missing evidence is a result. A checked promise with nothing verifiable is “No evidence kept”; an implied completion is “Likely done (inferred)”; records that disagree are “Contradicted” until the advisor rules, and even then the ruling is shown as hers.
  • Permissions are in Postgres. Row-level security on every table. An item inherits the most restrictive level of its messages; evidence is borrowed from a linked record only when everyone who reads the item may also read the other. Sealed placeholders come from a separate table with no source text.
  • Leaks are tested at three layers. In memory (no stored text at a more open level than a restricted fact it carries); in the database (every row of every table, view and function, per role, after a full run and sign-off); in the browser (every page and every source-message URL, as every role). Each test also proves someone allowed does see the text. Result: zero leaks.
  • Audit and immutability. Every review action, answer and reply writes an audit row with actor, action, reason, before and after, readable only by those who may read the item.
  • Data handling. Uploaded files are not stored; deleting a workspace removes all of its data; the service-role key never leaves the server; all demo data is synthetic and labelled.
05Decisions

Important technical decisions

DecisionWhy
Status and trust computed by fixed rules in a database triggerNo client, reviewer or model can set them; they follow every change of evidence, including a file being removed.
“Corroborated” needs independenceTwo records from different files or different people. One person promising and then saying it was done stays “sourced”.
Linked, never mergedA chat promise and its Trello card stay two records, each with its own level and quotes, so merging can never publish a restricted record.
A weak inference may not raise an item’s levelFound in testing: a vague hint in a finance chat hid a committee item from the incoming lead. Only plain “done” or “not done” from a more restricted record now counts.
Browser-driven job runnerVercel Hobby limits function time and Supabase Free has no workers; small steps keep every call short and show progress.
Two-step sign-offThe lead marks ready, the advisor approves only while that mark still matches; an accepted item changed by a later run must be accepted again.
Per-visitor demo clubsEach judge gets a workspace with four accounts of their own (passwords derived on the server, never stored), deleted after seven days, so nobody sees another visitor’s changes and RLS is exercised for real.
A frozen real-model ledger for the built clubA 160-call build cannot run inside one 60-second request, and judges should not wait or pay. The year club’s ledger is the stored output of one real run through the app’s own pipeline.

Automated tests: 395 unit tests, 185 database (row-level security) integration tests and 48 end-to-end browser tests, all passing. They include the whole flow a judge follows (four files at four levels → build → review → approve → hand over → question and reply) and the three-layer leak tests.

What the tests found and fixed, among others: the outgoing lead’s own private chat produced no items; a weak inference hid an item from the incoming lead; a hedge was missed when the quote left out “Maybe”; two semesters’ identical promises were wrongly linked; Trello to-do descriptions were read as promises.

Structured feedback from users: none yet. The Round 1 interviews were not carried out (see 08).

09Limits

What does not work yet

  • In the built year club the model proposed six items that are not real promises (left as drafts for review), linked one Trello card to the wrong semester’s promise, marked one done item only “Likely done”, and missed one recurring duty.
  • Acknowledgements are per item: a new version asks the incoming lead about every item again. A reply belongs to one answer; if she answers the item again, older replies leave the page (they stay in the audit history).
  • A daily budget of 500 uncached model calls protects the free demo; when it is used up, building stops with a message. The sample files and the built club use saved answers.
  • Uploads are limited to about 3.9 MB per import (Vercel’s request size). Unknown export formats are refused with an error rather than guessed.
  • The automated leak checks search for restricted text literally; a paraphrase would not be caught by them.
  • The Gaps tab lists a linked record’s gap separately from its twin. No accessibility audit has been done yet.
10Round 3

Three improvements committed for Round 3

IMPROVEMENT 1

Find recurring duties nobody wrote down

Today a duty is found only when the records state the rule. Round 3 infers duties from repetition alone: the same task done at about the same point in two or more past cycles (“lab permission requested in week 1, in both past years”). It computes a start-by date from how long past occurrences took. Each such duty is labelled Inferred and lists the occurrences it rests on. For the user: routine work the outgoing team never thought to mention appears in the incoming lead’s calendar with a start date, instead of being discovered late.

IMPROVEMENT 2

Gap questions for the outgoing lead

Every gap the records cannot close (a promise with no follow-up, a duty with no approver or date, an unruled conflict) becomes one short question on a single page. Each answer is recorded with the lead’s name as a labelled source (“stated by the outgoing lead”), passes the same trust and audit rules, and updates the next version. For the user: the handover is completed while the outgoing lead can still be asked, and every remaining unknown is either answered or knowingly left open.

IMPROVEMENT 3

Counterparty handoff notes

For each person or office the club owes something to (a sponsor, a lab in-charge, a department office), Inheritance drafts a short change-of-contact note: what is still owed, by when, and the new contact. It is built only from that counterparty’s approved items, so it cannot include restricted text. The outgoing lead edits and approves it, and the counterparty opens it from a signed link and acknowledges it; the acknowledgement shows on the handover. For the user: people outside the club learn of the handover too, so the old committee’s promises are not lost on the other side.

11Disclosure

Disclosures

  • AI in the product: the Claude API (Haiku 5.5) proposes items from the records; deterministic code and the database decide what is stored, its trust, status, dates and access level. The built demo club’s ledger is stored output from one real model run on synthetic data; which items start as accepted was decided by code from the ground truth.
  • AI in development: Claude Code (Anthropic) was used as a pair programmer for code, tests, migrations, the synthetic scenarios and documentation. Design decisions and every commit were reviewed by the developer.
  • Templates and data: standard Next.js and shadcn/ui starters; every person, club and message in the demo and the repository is invented. Details: docs/ai-disclosure.md, docs/changes-from-round1.md.
